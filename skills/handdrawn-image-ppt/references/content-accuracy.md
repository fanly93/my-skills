# 内容准确性与事实边界

## 事实优先级

1. 用户提供的产品事实、案例和明确的业务规则。
2. 用户指定的官方官网、产品文档、公开仓库和版本说明。
3. 原 PPT 中已经出现且能被定位的文字、图示和案例。
4. 对没有证据的内容只写“概念示意”“待核实”或不写。

不要因为竞品公开文档没有某项描述，就断言竞品不具备该能力。比较时注明版本、地区、预览状态、自托管/云服务范围和资料日期。

## 架构图的边界

可以画：角色、能力资产、资源授权、知识依据、版本、发布、运行记录、独立 Runtime 的接入关系，以及已被资料支持的连接器和治理对象。

不要凭“常见 Agent 架构”添加：原生长期记忆引擎、沙箱、浏览器、断点恢复、自动灰度回滚、调度算法、全链路 Trace、性能指标或私有化承诺。若用户需要比较这些维度，先查证并在图中标注公开资料范围。

## 案例连续性

当用户给了一个案例，跨页重复同一个对象、编号和业务目标；把新增页定位为原稿的“能力交付、安装使用、资源治理、复用或比较”补充，避免重新讲一遍原稿已有流程。保留编号本身，不解释未提供的故障代码、根因或因果关系。需要演示“版本”时，用“已发布版本”“当前适用资料”等易懂说法，不为了造例子添加陌生版本号。

## 人工确认门控

涉及审批、付款、CAPA、变更、发送或写回业务系统时，严格画出：结果/建议 → 复核 → 负责人确认/授权 → 创建或执行。分析结果不等于审批通过，建议不等于系统写回。

## 光启案例的历史经验（仅作参考，不是每个新项目的固定内容）

本次成功项目使用了设备 M-240A 的 E37 报警贯穿架构和竞品页；其中 Luban 面向开发/PM/FDE，CoCoAI 面向业务安装使用，Lumen 是共同底座。未来主题变更时只保留这套“同一案例贯穿、三产品职责清楚、确认门控明确”的方法，除非用户要求继续讲光启，否则不要自动带入这些名称。
